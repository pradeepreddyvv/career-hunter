Key Technical Decisions

Why scheduled sync instead of real-time sync from AnyPoint Exchange/GoCD?▼

AnyPoint Exchange has rate limits (polling every few seconds would hit them). API metadata changes are infrequent (~10-20/day across 2000+ APIs). 4-hour lag is acceptable. Three different source systems with different auth mechanisms — syncing all three continuously would add complexity for minimal benefit. All platforms expose REST APIs: MuleSoft via AnyPoint Exchange REST API (OAuth2, 100/page pagination), Spring Boot via internal platform APIs, Kong via Kong Admin API. Each adapter maps platform-specific fields to a unified ApiInventoryDTO, then single Oracle upsert.

MySQL → Oracle migration — 3 latent bugs + SUBSTR production blocker▼

Oracle syntax differences required careful migration:

  • IF() → CASE WHEN in all 50+ JPA queries
  • MEDIUMBLOB → Oracle BLOB with JPA @Lob annotation update
  • ORA-00904 (invalid identifier) from JPA column name mismatches → fixed @Column(name=) annotations
  • 3 latent bugs found: (1) WHERE col = NULL instead of IS NULL — deprecated APIs showing as active; (2) MySQL lenient GROUP BY hiding wrong api_version in reports; (3) ORDER BY assumption — time-series report in random order not chronological
  • Production blocker: SUBSTR not installed on prod Oracle — ORA-06553 during cutover. Had to raise formal DBA change request. Maintenance window rescheduled by 2 days.
  • Tested 100% in local Oracle Docker before UAT
DuplicateKeyCheckFilter — security hardening▼

Jackson silently accepts duplicate JSON keys, using the last value. Attack: {"userId":"legit@bank.com","userId":"admin@bank.com"} — validation sees first value, controller gets last. Built DuplicateKeyCheckFilter using Jackson streaming parser. Key challenge: HttpServletRequest.getInputStream() can only be read once. Built CachedBodyHttpServletRequest wrapper: buffers bytes on first read, returns fresh ByteArrayInputStream on subsequent reads. Filter reads body (duplicate check), controller reads from buffer. Applied globally via Spring Security chain — zero controller changes.

Live / Non-Live mode toggle▼

Map<String, Node> nodeMap = new LinkedHashMap<>();
for (Node node : nodes) {
    nodeMap.put(node.getPath(), node);
    String parentPath = getParentPath(node.getPath());
    if (parentPath != null && nodeMap.containsKey(parentPath)) {
        nodeMap.get(parentPath).addChild(node);
    }
}

Why least-connections, not round-robin?▼

Cache hit requests complete in ~50ms. Cache miss requests go to Mastercard/CERSAI and take ~800ms. Round-robin distributes evenly by count — a node that received a cache miss request is still serving it when round-robin sends it another request. Least-connections routes new requests to the node currently handling fewest active connections, naturally accounting for response time variance.

Why SHA-256(PAN) as cache key, not raw PAN?▼

Storing raw PAN in Redis key means PAN is visible in Redis key-space scans, logs, monitoring tools. SHA-256 is a one-way hash — the Redis key reveals nothing about the PAN. Still deterministic (same PAN always hashes to same key), so cache lookups work. PAN is 10-character alphanumeric — SHA-256 prevents brute-force from Redis key exposure.

JWT token race condition prevention▼

If Redis TTL exactly matches JWT expiry, there's a race: token retrieved from cache, expires in-flight before the downstream API call completes. Solution: cache TTL = JWT expiry - 5 minutes buffer. Token is always valid for at least 5 more minutes when retrieved from cache. Combined with a token refresh lock (Redis SET NX) to prevent thundering herd on expiry.

Kafka for async DB writes — why not thread pool?▼

Thread pool: if Oracle is slow/down, threads pile up, backpressure hits the API response. With Kafka: producer publishes to topic and returns immediately — Oracle write fully decoupled. Messages survive restarts. DLQ (Dead Letter Queue) for failed writes. Idempotent consumer (message ID check prevents duplicate DB inserts on retry). Thread pool doesn't give you persistence or replay — Kafka does.

Aadhaar compliance — AadhaarMaskingFilter▼

UIDAI mandate: Aadhaar numbers cannot appear in logs. Log4j2 custom filter AadhaarMaskingFilter uses regex \b\d{12}\b to replace any 12-digit Aadhaar pattern with AADHAAR-MASKED in ALL log messages before they're written. Also: AES-256-CBC encryption before sending to UIDAI, Oracle TDE column encryption for enterprise_RECORDS table, Kafka messages sanitized before write.

Key Technical Decisions

Why cursor-based pagination, not offset pagination?▼

Offset pagination: OFFSET 1000 LIMIT 20 — DB must scan and discard 1000 rows to return rows 1001-1020. As offset grows, query gets slower. For rural field agents with 500+ assigned customers, page 25 (offset 500) would be noticeably slow on mobile. Cursor pagination uses SFDC's nextRecordsUrl — SFDC maintains a server-side cursor, each page request uses the cursor from the previous response. O(1) per page regardless of how deep into the list you are.

Redis JWT cache for SFDC tokens — why AES encrypted?▼

SFDC JWT token gives access to the entire SFDC org. Storing it in Redis as plaintext means anyone with Redis access (ops, monitoring tools, Redis browser) can read it and make SFDC API calls directly. AES-256 encrypts the token value in Redis. The encryption key is in application config (not Redis). Even if Redis is compromised, tokens are unreadable without the key.

Why DataWeave for SFDC→Mobile transformation?▼

DataWeave is MuleSoft's native transformation language — zero additional library dependencies, compiled to bytecode, much faster than Java-based JSON manipulation. SFDC returns nested attributes metadata, dot-notated field names like Contact__r.Name, and datetime formats incompatible with Android's JSON parser. DataWeave maps these to flat, clean JSON with proper ISO 8601 dates and human-readable field names in a single declarative expression.

Key Technical Decisions

Why internal LLM? (Not OpenAI/Claude/Gemini)▼

RBI Circular on Cloud Computing + DPDP Act 2023: partner and customer financial data cannot leave India or be processed by foreign cloud providers. Emails contain loan amounts, account references, customer names — all PII. Sending to OpenAI/Anthropic APIs would route data through US data centers — a direct RBI violation. Previous Company's internal AI team built and maintains their own LLM deployed on-premise. Same REST API interface. All data stays on Previous Company's internal network.

Privacy pre-filter — three layers before LLM▼

Layer 1: Keyword routing — CONFIDENTIAL/RESTRICTED in subject/body → skip LLM, route to human queue immediately. Layer 2: PII regex masking — Aadhaar (12-digit) → [AADHAAR-MASKED], PAN (ABCDE1234F) → [PAN-MASKED], account numbers → [ACCOUNT-MASKED]. LLM sees masked text — still understands context, drafts sensible reply. Layer 3: Sender domain whitelist — only @idfcfirstbank.com processed; external senders → human queue regardless. Defense in depth: LLM never sees raw PII.

Why temperature=0.3?▼

Temperature 0.0 = completely deterministic — same prompt → same output always. If you process 20 "service is down" emails, every draft reply is identical, word for word. Recipients notice robotic repetition. Temperature 0.3 = slight phrasing variation while keeping semantic content precise and factual. Hallucination risk stays low. 0.7+ → risk of LLM inventing information not in the email — dangerous in financial communications.

MS Graph API — Application vs Delegated permissions▼

Delegated permissions: app acts on behalf of a signed-in user — requires interactive browser login. Token tied to user session. Impossible for an unattended background service. Application permissions: app acts as itself using client_id + client_secret + certificate. No user session needed. Runs 24/7 unattended. Mail.Read scope reads the team's shared inbox without any human login.

Outlook add-in frontend — UI flow▼

Add-in loads in Outlook reading pane when you open an email. Three panels: (1) Summary — AI-generated plain-English summary of the incoming email. (2) Reply draft — AI-suggested reply based on email content. (3) Content type input — text field where team lead specifies what kind of response is needed (e.g., "escalate to DevOps", "ask partner for redirect URI") → triggers a refined second LLM call. Three action buttons: Approve (copies draft to Outlook compose for final human review and send), Edit (opens editable text area), Reject (routes to human-only handling). Human always manually sends — zero auto-send.

Why human-in-the-loop (why not auto-send approved drafts)?▼

Financial sector requirement: all external communications must be reviewed by a human before sending. LLMs at temperature=0.3 are precise but can occasionally produce responses that are factually correct but tonally inappropriate for a regulated financial institution. The 30% time savings comes from not drafting from scratch — not from removing human judgment. Human approves, edits, and manually clicks Send.

Project 1: API Inventory Portal

✅ Done Correctly
Adapter pattern for multi-platform sync is textbook correct — one interface, per-platform implementations, unified DTO. Rules engine as DB-driven config (not hardcoded) was the right call for a regulated environment where rules change quarterly. CachedBodyHttpServletRequest to enable multi-read of request body for DuplicateKeyCheckFilter is exactly the right pattern. Spring Filter (not interceptor, not controller) for universal HTTP-layer protection is correct. UAT→pre-prod→prod data pipeline is pragmatic given the security boundary constraint (no direct prod-to-lower-env connection).
❌ Suboptimal / What Could Be Better
Polling-based sync: Calling AnyPoint Exchange REST API + Kong Admin API + Spring Boot APIs every N minutes scans all 2000+ APIs regardless of changes. If 1990 APIs haven't changed, 1990 API calls were wasted. Better: event-driven CDC or webhooks — only changed APIs trigger sync.

Rules engine performance: DB-loop through all active rules for every API × 2000 APIs = potentially 2000 × N DB reads per compliance check cycle. For 50 rules and 2000 APIs this is 100,000 DB operations. Should cache rules in-memory (refreshed on change), then evaluate in-process.
🚀 If Starting Fresh — Optimal Approach
Sync: Debezium CDC on each platform's DB → Kafka → consumer updates Oracle. Near-real-time, zero polling. For platforms without DB access (AnyPoint Exchange), use webhooks where available + incremental polling (WHERE updated_at > last_sync) as fallback.

Compliance Engine: Drools or SpEL-evaluated rule specs stored as JSON in DB. Rules loaded at startup into an in-memory RulesCache. Refreshed via @RefreshScope or Redis Pub/Sub on admin change. Every API evaluated against 50 rules in microseconds in-process.

Security Filter: Kong custom plugin (Lua) validates no duplicate JSON keys at gateway. Applies to all services, zero per-service code. Add WAF rules for common JSON injection patterns.

Project 2: Developer Portal

✅ Done Correctly

❌ Suboptimal / What Could Be Better

AES encryption with shared key in config: Symmetric key stored in application.properties or env var is a rotation and leakage risk. The key is the single point of failure — if leaked, all encrypted data is exposed retroactively. Should use envelope encryption: data encrypted with a data key, data key encrypted with a master key in a KMS (AWS KMS or HashiCorp Vault). Rotate master key without re-encrypting all data.

3rd party email via Spring Boot: OTP sent directly from Spring Boot. If the email provider goes down, registration breaks entirely. Should have a retry mechanism + fallback to a secondary provider.

Project 3: high-throughput APIs

✅ Done Correctly

Resilience4J circuit breaker on UIDAI is correct for external API resilience. UIDAI error code mapping to business-readable messages is good UX engineering. ❌ Suboptimal / What Could Be Better

Fixed circuit breaker thresholds: Resilience4J configured with fixed failure count (e.g., 5 failures → open). UIDAI has different failure patterns for different error types: authentication failures (4xx) should never open the circuit — they indicate bad input, not UIDAI being down. Circuit should only open on 5xx + timeouts. Requires careful exception type configuration in @CircuitBreaker.

Kafka without Outbox Pattern: If the enterprise service crashes after sending the Kafka message but before confirming the API response, the customer sees an error but the Kafka message was already sent → duplicate processing possible. Outbox pattern + Debezium eliminates this: write to outbox table in same Oracle transaction as response → CDC publishes to Kafka atomically.
🚀 If Starting Fresh — Optimal Approach
Cache Key Security: HMAC-SHA256(pan, secret_key) as Redis key. Secret key in HashiCorp Vault, auto-rotated every 90 days. Redis at-rest encryption. Three-layer PII protection in cache.

Kafka Reliability: Outbox Pattern + Debezium. Write KycAuditOutbox record in same Oracle transaction as API response. Debezium CDC publishes to Kafka from outbox table. Exactly-once semantics without manual idempotency checks. Dead Letter Topic + PagerDuty alert for consumer failures.

UIDAI Integration: Bulkhead (dedicated 50-thread pool for UIDAI calls) + CircuitBreaker (5xx/timeout only) + TimeLimiter (adaptive p99+20% timeout) + Retry (3 attempts, 500ms/1s/2s, 5xx only). Q: Why Promise.allSettled instead of Promise.all for the 3 external API calls?
Promise.all fails fast — if any one of O*NET, JSearch, or BLS throws, the entire analysis fails. Promise.allSettled waits for ALL to settle (fulfilled or rejected) and returns an array of results. If BLS is down, the career analysis still runs with O*NET + JSearch data. Graceful degradation: each data source is optional enrichment, not a hard dependency. O*NET is the most critical (occupational skills), JSearch is important (live job count), BLS is nice-to-have (macro trend). With allSettled, a BLS outage doesn't break the product.
Q: How does Gemini function_calling give you structured output instead of free text?
Gemini's function_calling mode is equivalent to OpenAI's tool_use. You define a JSON schema for the career_transitions function with typed fields (feasibility: enum['strong','moderate','stretch'], salaryDelta: number, etc.). Gemini returns a tool_calls response with arguments matching that schema — not free text. The response is parsed directly as typed JSON. Benefits: (1) No regex parsing of LLM output. (2) Validation at deserialization — wrong type is caught immediately. (3) Enforces completeness — all required fields must be present. This is why WorkShift's cards are structured and consistent, not variable-length prose.

Problem Solved: The GeoJSON conversion challenge — why was 03_fix_all_data.py needed?
The raw NYC CSV had LOCATION field in 3 broken formats: (1) String: '(40.7580, -73.9855)' — not valid JSON. (2) Integer/null: some records had 0 or null for LOCATION. (3) Coordinates (0.0, 0.0) — invalid coordinates (null island, not NYC). MongoDB's 2dsphere index rejects documents with invalid geometry — if even one document has bad LOCATION, the index build fails. Fix: regex to parse string coordinates, convert to {type:'Point', coordinates:[lng, lat]} (GeoJSON is longitude-first — critical, many developers get this wrong). Records with (0.0, 0.0) coordinates: set LOCATION to null and exclude from index with sparse:true option.
Problem Solved: Why checkpoint-based embedding generation?
2M records × BATCH_SIZE=500 = 4000 batches. FastEmbed generates 384-dim vectors using ONNX Runtime — fast, but a full run takes hours on a CPU server. Servers can restart (OOM, maintenance). Without checkpointing, a restart = start from zero. Checkpoint file stores: {processed: 450000, last_id: 'ObjectId(...)'}. Resume: query MongoDB for documents with _id > last_id AND embedding doesn't exist. Process remaining. The last_id approach is more reliable than offset pagination at scale — MongoDB's SKIP at high offsets is O(n), while _id comparison is O(log n) with the default _id index.

Q: Why MongoDB over PostgreSQL + PostGIS for geospatial + vector search?
MongoDB Atlas supports both $nearSphere (geospatial) and $vectorSearch (semantic) natively — one database, no extensions. PostgreSQL with PostGIS + pgvector would work but requires: installing PostGIS extension, installing pgvector extension, separate index creation for each. MongoDB's document model also fits the crash data naturally — variable number of contributing factors (1-5) stored as a document, not 5 nullable columns in a relational table. The $vectorSearch aggregation pipeline chains with $geoNear and $match in a single query — compound geo + semantic search in one round trip.
Q: Explain $nearSphere vs $near vs $geoWithin.
$nearSphere: spherical distance model (accounts for Earth's curvature). Returns documents sorted by distance (nearest first). Requires 2dsphere index. Use for: 'find X crashes closest to this coordinate'. $near: flat (Euclidean) distance model. Use only for very small areas (city block level) where curvature is negligible. $geoWithin: finds documents within a shape (polygon, circle, box) but does NOT sort by distance. Use for: 'how many crashes happened in this neighborhood polygon?' (just a count/filter, not ranked by proximity). For crash analysis near a specific point, $nearSphere is correct — distance matters and city-scale queries need spherical model.
Q: What is FastEmbed and why use it over HuggingFace transformers?
FastEmbed is an Onnxruntime-based embedding library by Qdrant. Key difference: ONNX Runtime instead of PyTorch. PyTorch loads the full training framework even for inference — heavy memory footprint, slower startup. ONNX Runtime: optimized inference only, ~3x faster for batch embedding, lower memory. BAAI/bge-small-en-v1.5 (384 dimensions, 33M parameters): excellent quality/speed tradeoff. For 2M crash records, using HuggingFace transformers would have taken 3x longer. FastEmbed also handles tokenization, batching, and OOM recovery internally.
Q: How would you implement hybrid search (keyword + semantic)?
MongoDB Atlas Search supports Reciprocal Rank Fusion (RRF) hybrid retrieval. The pipeline: (1) BM25 text search stage: $search with text operator on contributing_factor, borough fields — keyword matching. (2) Vector search stage: $vectorSearch on the embedding field — semantic matching. (3) RRF fusion: $rankFusion operator combines scores from both stages. Query 'drunk driving fatalities in Brooklyn 2024' benefits from: BM25 matching 'drunk', 'fatalities', 'Brooklyn', '2024' as keywords AND semantic matching crash descriptions similar to 'alcohol impairment fatal accident'. Hybrid consistently outperforms pure vector search on structured data with known terminology.
Q: How does the geohash add value beyond the GeoJSON coordinate?
Geohash encodes lat/lng as a short string (e.g., 'dr5ru7' for Times Square area). Same geohash prefix = nearby location. Benefits: (1) Spatial bucketing: GROUP BY geohash[:5] aggregates crashes by neighborhood without polygon queries. (2) Faster approximate proximity: Redis can index geohashes for in-memory proximity queries (faster than MongoDB geospatial for hot cache). (3) Compact storage: 6-char geohash ≈ 1.2km precision — good for heatmap generation. (4) Consistent bucketing: geohash cells are stable — same cell boundaries for all records. Used in the analytics layer for heatmap data generation and borough-level aggregation caching.
Q: What is a MongoDB replica set and why was it needed?
A replica set is a group of MongoDB instances that maintain the same data: 1 primary (accepts writes) + 1+ secondaries (replicas). Required for: (1) Change streams ($changeStream) — MongoDB's CDC mechanism, requires replica set. (2) Multi-document transactions — require replica set. (3) High availability — if primary fails, a secondary is elected. For this project, the local replica set (replicaSet=rs0) was configured not for HA but to enable future change stream support — real-time crash reporting as new data arrives. Single-node replica set in development is a common pattern to keep parity with production Atlas (which is always a replica set).

Q: Walk through the Eye Aspect Ratio (EAR) drowsiness detection algorithm completely.
Step 1: Face detection using dlib's HOG-SVM frontal face detector → bounding box. Step 2: 68-point shape predictor regresses landmark coordinates within bounding box. Eye landmarks: left eye = indices 36-41, right eye = 42-47 (6 points per eye forming an ellipse). Step 3: EAR = (|p2-p6| + |p3-p5|) / (2 × |p1-p4|) where p1=left corner, p4=right corner, p2/p3=top landmarks, p5/p6=bottom landmarks. Open eye: EAR ≈ 0.3. Closed eye: EAR → 0. Step 4: If EAR < 0.25 for 20 consecutive frames (~0.67s at 30fps) → drowsiness alert (audio alarm + red overlay). The consecutive-frame threshold prevents single-blink false positives. Average EAR of both eyes used for robustness.
Q: Why is EAR better than a simple eye-closed/open classifier?
EAR is a geometric ratio — invariant to: face size (close camera vs far camera), image resolution, camera angle variation. A pixel-based classifier would need retraining for different cameras and distances. EAR works on the RELATIONSHIP between landmark points, which is stable across conditions. Also: EAR gives a continuous value (0 to 0.4), not a binary — you can set different thresholds for 'tired' (EAR slightly low) vs 'asleep' (EAR near zero). A binary classifier loses this gradation. Additionally, EAR computation is O(1) — 6 Euclidean distance calculations — vs a neural network forward pass for a classifier.
Q: How does Hough Transform detect lane lines?
Pipeline: (1) Grayscale → Gaussian blur (reduce noise). (2) Canny edge detection (gradient magnitude threshold). (3) Region of Interest mask: trapezoid shape covering the road ahead (bottom ~60% of frame). (4) Hough Line Transform: converts edge points to Hough space (ρ, θ), finds lines as peaks in accumulator array. Parameters: rho=1, theta=π/180, threshold=50 (min votes), min_line_len=100px, max_line_gap=50px. (5) Separate left lane (negative slope) from right lane (positive slope). (6) Average/extrapolate to full lane lines. Departure detection: if left lane x-position shifts right by >50px or right lane shifts left by >50px → lane departure warning.
Q: How did you optimize for Raspberry Pi's ARM CPU?
4 optimizations: (1) Frame skipping: drowsiness check on every 2nd frame (display at 30fps, process at 15fps) — drowsiness develops over seconds, 15fps detection is sufficient. (2) Resolution reduction: capture at 640×480 instead of 1080p — reduces pixel processing by 4x. (3) OpenCV DNN with ONNX quantized (INT8) models: INT8 quantization reduces model size by 4x and speeds up inference by 2-3x on ARM. (4) ROI-based processing: run face detection on full frame, but landmark prediction only within face bounding box — reduces landmark computation by 10x. Result: 15-20fps sustained on Raspberry Pi 4 (4GB RAM).

Q: Explain the Canny edge detection parameters you tuned for lane detection.
Canny has two thresholds: lower and upper. Pixel gradient > upper → strong edge (include). Gradient between lower and upper → weak edge (include only if connected to strong edge). Gradient below lower → not edge. For lane detection: lower=50, upper=150. Why these values: lane lines are painted markings — high contrast against asphalt (strong gradient). Too low an upper threshold: noise (cracks, shadows) gets included as edges. Too high: actual lane markings missed in shadows. The 1:3 ratio (50:150) is a standard starting point. Adjusted empirically: filmed 20 road segments, tuned until lane lines consistently detected without noise. Gaussian blur kernel size (5×5) was also tuned — larger blur removes more noise but smooths lane boundaries.
Q: What is model quantization and why does it matter for embedded AI?
Quantization reduces model precision: float32 (32 bits) → int8 (8 bits). Effect: model size ÷4 (from 200MB → 50MB), inference speed ×2-3 (integer arithmetic vs floating point). Accuracy loss: typically 1-3% on classification tasks — acceptable for real-time applications where speed matters more than marginal accuracy. For Raspberry Pi: (1) Limited RAM (4GB total, shared with OS). Large float32 models can cause OOM. (2) ARM's NEON SIMD instructions are optimized for integer operations — INT8 gets hardware acceleration. (3) Thermal: lower compute → less heat → sustained performance without throttling. Post-training quantization (TensorFlow Lite, ONNX Runtime) is the easiest path — no retraining needed.
